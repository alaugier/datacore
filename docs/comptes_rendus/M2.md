## 3. Décisions techniques et justifications

- **Approche bottom-up par datamarts** (Kimball), rendue tangible
  physiquement par 4 schémas Postgres distincts (`dimensions`,
  `exploitation`, `commercial`, `gouvernance`) dans une base dédiée, sur
  la même instance que le staging (sobriété RGESN, pas de second
  conteneur).
- **Ordre C13 → C14 → C15 → C17 → C16**, contrairement au Gantt initial
  (C16 avant C17) — documenté et justifié avant tout développement dans
  `sequencement_bloc3.md` : le SCD2 est un prolongement direct de l'ETL,
  et surtout la procédure de purge RGPD de C16 dépendait du schéma
  historisé que C17 devait d'abord créer.
- **Rechargement complet à chaque exécution ETL, sauf deux exceptions** :
  `dim_temps` (générée, pas rechargeable depuis staging) et `dim_client`
  (historisée SCD2 depuis C17, une troncature détruirait l'historique).
- **Écart assumé avec la description de l'issue #48** : le SCD2 devait
  historiser « adresse ou contrat client », des attributs absents du jeu
  de données (`clients` FluxPro n'a que id/code/nom/secteur) — tranché
  avec l'utilisateur avant implémentation, `nom`/`secteur` retenus comme
  attributs suivis.
- **Bug latent Alembic corrigé** (C17) : `env.py` de l'entrepôt ne
  passait pas `include_schemas=True`, invisible depuis C14 (une
  migration contre une base vide masque ce type de bug), révélé par la
  seconde migration.
- **Sauvegarde partielle vs. complète** (C16) justifiée par la
  reconstructibilité : 7 des 8 tables sont intégralement rejouables
  depuis le staging via l'ETL, seule `dim_client` (historisée) ne l'est
  pas — la sauvegarde partielle protège spécifiquement cette donnée.
- **Journalisation sur connexion séparée** (C16) : si la transaction de
  chargement est annulée, la ligne de journal décrivant l'échec doit
  malgré tout être conservée.
- **Registre RGPD de l'entrepôt : aucune donnée personnelle trouvée**,
  résultat direct des choix RGPD *by design* pris dès C13 — appuyé par
  un contrôle automatisé répétable (`audit_rgpd.py`), pas seulement une
  conclusion documentée à un instant donné.
- **matplotlib introduit** (C16, premier usage de visualisation dans le
  projet) pour le tableau de bord SLA — décision validée avec
  l'utilisateur plutôt que supposée, alternative texte-seul envisagée.

## 5. Points ouverts / risques pour la suite (M3 — Data Lake OMEGA LAKE)

- Le tableau de bord SLA est livré sous forme de vues SQL + notebook,
  pas un outil de BI dédié (aucun outil imposé par le référentiel) — à
  réévaluer si un outil de reporting partagé devient nécessaire pour la
  suite du programme ou le rapport final.
- `dimensions.dim_client` compte désormais plusieurs versions par
  client (SCD2) ; aucune purge RGPD requise (pas de donnée personnelle),
  mais une politique de rétention de confort pourrait se justifier si le
  volume grandissait significativement — non nécessaire à ce stade.
- Les sauvegardes planifiées sont documentées (script + exemple
  crontab) mais aucun ordonnanceur n'est réellement actif dans
  l'environnement Docker Compose local — à mettre en place si le
  programme passe en environnement de déploiement réel.
- Le prestataire SupervIT n'est toujours pas mobilisé (prévu en
  Phase 4, cf. `supervision_projet.md`) — pertinent pour M3 (data lake,
  IoT), à activer à ce moment-là.
- Le staging reste la seule source de vérité pour l'ETL de l'entrepôt ;
  si le data lake (M3) doit absorber des données IoT massives, définir
  comment il s'articule avec le staging et l'entrepôt déjà en place
  (flux séparé, ou alimentation croisée) sera un point de conception à
  trancher explicitement avant de coder, sur le même principe que
  `sequencement_bloc2.md`/`sequencement_bloc3.md`.
