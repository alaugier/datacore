## 3. Décisions techniques et justifications

- **Séquencement C8 → C10 → C9 → C11 → C12** (et non « modéliser d'abord ») : documenté et justifié avant tout développement dans `sequencement_bloc2.md`, validé par l'expérience (le grain réel des doublons n'a été découvert qu'en traitant concrètement les données, pas en les modélisant à l'avance).
- **Zone d'atterrissage intermédiaire** `data/interim/` (non versionnée) entre C8/C10 et C11.
- **Historique chargé dans la même base de staging PostgreSQL** plutôt qu'un outil « big data » dédié : volume réel (25 000 lignes) disproportionné pour un outil séparé, choix justifié par la sobriété (RGESN).
- **Alembic** pour versionner uniquement les tables que le programme modélise lui-même (`transporteurs`, `tournees`, `livraisons`, `commandes_clients`, `lignes_commande_clients`) — les tables FluxPro (schéma fourni) et `historique_expeditions` restent hors de son périmètre.
- **Analyse des formes normales empirique** (pas théorique) : a révélé deux violations réelles, corrigées après vérification chiffrée sur les données — `livraisons.statut` (3NF, remplacé par une vue SQL) et `commandes_clients` plate (2NF, décomposée en-tête/lignes, colonnes redondantes avec `produits` FluxPro supprimées).
- **FastAPI plutôt que Flask** pour l'Omega Data API (C12) : génération automatique de la spécification OpenAPI exigée par le livrable, sans maintenance manuelle d'un fichier séparé.
- **Autorisation par groupe** reprise du registre RGPD (C11) : référents clients externes systématiquement restreints à leur client, sans accès aux données de transport (`/livraisons`).
- **mypy ajouté à la CI** (job `typecheck`), corrige au passage deux vrais trous de robustesse dans le scraping du portail transporteur (C8, code déjà mergé).

## 5. Points ouverts / risques pour la suite (M2 — Entrepôt OMEGA BI)

- L'Omega Data API n'expose pas la totalité des tables de la base de
  travail (pas d'endpoint direct sur `produits`, `clients`, `stocks`
  FluxPro) — choix de périmètre délibéré (le jeu de données *consolidé*,
  cœur du Bloc 2, plus un KPI à valeur ajoutée), à réévaluer si le bloc 3
  (entrepôt OMEGA BI) a besoin d'un accès direct à ces tables via l'API
  plutôt que par requête SQL directe sur la base de staging.
- Le rapprochement `clients.nom` (FluxPro) ↔ `historique_expeditions.client`
  (libellé texte libre) reste non garanti par une contrainte — à traiter
  formellement lors de la modélisation de l'entrepôt de données (C13),
  comme déjà anticipé en C9 et C11.
- `commandes_clients` reste indépendante de `commandes` (FluxPro), faute
  de clé métier commune dans le jeu de données pédagogique — point à
  garder en tête si le bloc 3 a besoin de croiser les deux flux de
  commandes (client brut vs. traité par Omega).
- Le prestataire SupervIT n'est toujours pas mobilisé (prévu en Phase 4,
  cf. `supervision_projet.md`) — sans impact sur M1/M2.
